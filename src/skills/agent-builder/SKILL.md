# Agent Builder

为任意领域构建 AI Agent——客户服务、研究、运营、创意工作或专业业务流程。

## 核心理念

> **模型已经知道如何成为一个 agent。你的工作是不要挡它的路。**

Agent 不是复杂的工程。它是一个简单的循环，邀请模型采取行动：

```
循环：
  模型看到：上下文 + 可用能力
  模型决定：行动或回应
  如果是行动：执行能力，添加结果，继续循环
  如果是回应：返回给用户
```

**就是这样。** 魔法不在代码中——而在模型中。你的代码只是提供机会。

## 三要素

### 1. 能力（它能做什么？）

Agent 可以执行的原子操作：搜索、读取、创建、发送、查询、修改。

**设计原则**：从 3-5 个能力开始。只有当 agent 因为缺少某个能力而持续失败时，才添加更多。

### 2. 知识（它知道什么？）

按需注入的领域专业知识：策略、工作流、最佳实践、模式。

**设计原则**：让知识可用，而非强制。在相关时加载，而不是一开始就全部加载。

### 3. 上下文（发生了什么？）

对话历史——将行动连接成连贯行为的线索。

**设计原则**：上下文是宝贵的。隔离嘈杂的子任务。截断冗长的输出。保护清晰度。

## Agent 设计思维

在构建之前，先理解：

- **目的**：这个 agent 应该完成什么？
- **领域**：它在什么世界中运作？（客户服务、研究、运营、创意……）
- **能力**：哪 3-5 个行动是必不可少的？
- **知识**：它需要访问什么专业知识？
- **信任**：你可以把哪些决策委托给模型？

**关键**：信任模型。不要过度工程化。不要预先指定工作流。给它能力，让它自己推理。

## 渐进式复杂度

从简单开始。只有当实际使用暴露了需求时，才增加复杂度：

| 级别 | 添加什么 | 何时添加 |
|------|----------|----------|
| 基础 | 3-5 个能力 | 始终从这里开始 |
| 规划 | 进度追踪 | 多步骤任务失去连贯性时 |
| 子 agent | 隔离的子 agent | 探索污染了上下文时 |
| 技能 | 按需知识 | 需要领域专业知识时 |

**大多数 agent 永远不需要超越第 2 级。**

## 领域示例

**业务**：CRM 查询、邮件、日历、审批
**研究**：数据库搜索、文档分析、引用
**运营**：监控、工单、通知、升级
**创意**：资源生成、编辑、协作、审阅

模式是通用的。只有能力在变化。

## 关键原则

1. **模型就是 agent** —— 代码只是运行循环
2. **能力赋能** —— 它能做什么
3. **知识指导** —— 它知道怎么做
4. **约束聚焦** —— 限制创造清晰度
5. **信任解放** —— 让模型推理
6. **迭代揭示** —— 从最小开始，从使用中演进

## 反模式

| 模式 | 问题 | 解决方案 |
|------|------|----------|
| 过度工程化 | 在需要之前就复杂化 | 从简单开始 |
| 能力过多 | 模型混乱 | 初始 3-5 个 |
| 僵化的工作流 | 无法适应 | 让模型决定 |
| 前置加载知识 | 上下文膨胀 | 按需加载 |
| 微观管理 | 削弱智能 | 信任模型 |

## Agent 思维模式

**从**："我如何让系统做 X？"
**到**："我如何让模型能够做 X？"

**从**："这个任务的工作流是什么？"
**到**："什么能力可以帮助完成这个任务？"

最好的 agent 代码几乎是无趣的。简单的循环。清晰的能力。干净的上下文。魔法不在代码中。

**给模型能力和知识。信任它来完成剩下的工作。**
